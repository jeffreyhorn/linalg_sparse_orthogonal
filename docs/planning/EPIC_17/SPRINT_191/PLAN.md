# Sprint 191 Plan: Bounded External Comparison Family

**Sprint Duration:** 14 days
**Goal:** Add one bounded external comparison family that improves numerical
credibility without claiming broad ecosystem parity.

**Time budget:** Each day is capped at 12 hours as requested. This day-by-day
plan totals `168` hours, matching the Sprint 191 estimate in the Epic 17
project plan.

**Primary scope:** Select exactly one additional external comparison family,
define its fixture, reference implementation, metrics, tolerances, dependency
policy, runner outputs, report-index metadata, tests, documentation, and
validation gates while keeping the claim surface intentionally narrow.

**Non-goals:** Broad sparse linear algebra ecosystem parity, performance
leadership claims, package-manager expansion, shared-library support,
unbounded benchmark families, multiple new comparison families, dynamic ABI
claims, or promotion of unreviewed external dependencies.

---

## Day 1: Sprint Intake and Candidate Baseline

**Title:** Comparison Family Intake
**Theme:** Establish the Sprint 191 scope, current comparison infrastructure,
and candidate-selection boundaries.
**Time estimate:** 12 hours

### Tasks

1. Re-read the Sprint 191 section of the Epic 17 project plan and map items
   191.1 through 191.6 to owner files, scripts, tests, and documentation.
2. Review Sprint 187 acceptance gates and Sprint 190 selected comparison

3. Inventory existing comparison runner targets, report rows, manifest fields,

4. Identify candidate solver families that could be added as one bounded
   external comparison without broad ecosystem-parity claims.
5. Create `WORKING_NOTES.md` with baseline findings, candidate list,
   selection criteria, risks, and Day 2 audit questions.

### Deliverables

- Sprint 191 working-notes scaffold.
- Current comparison infrastructure inventory.
- Candidate family list.
- Selection criteria and risk register.

### Completion Criteria

- Sprint scope is traceable to items 191.1 through 191.6.
- Existing selected comparison infrastructure is understood before new work
  begins.
- Candidate selection is constrained to one bounded family with explicit
  rejection criteria.

## Day 2: Candidate Family Audit

**Title:** Family Selection Audit
**Theme:** Compare candidate families by numerical value, dependency risk,
fixture size, and implementation cost.
**Time estimate:** 12 hours

### Tasks

1. Score each candidate family against acceptance tolerances, solver coverage,
   reference availability, dependency licensing, determinism, and CI cost.
2. Inspect whether each candidate can be represented by source-controlled
   fixture material and deterministic generated report rows.
3. Identify platform and toolchain assumptions for the likely reference
   implementation, including optional dependency behavior.
4. Rank candidates by smallest credible evidence gain with lowest maintenance
   and review surface.
5. Record the selected family and at least one rejected alternative with
   concrete rationale.

### Deliverables

- Candidate family audit artifact.
- Ranked selection table.
- Selected family decision.
- Rejected alternative rationale.

### Completion Criteria

- Exactly one family is selected for implementation.
- The selected family has known fixture, reference, metric, and dependency
  boundaries.
- Rejected candidates have recorded reasons that prevent scope creep later in
  the sprint.

## Day 3: Fixture and Metric Contract

**Title:** Fixture Contract
**Theme:** Define the source-controlled fixture, expected numerical behavior,
and comparison metrics for the selected family.
**Time estimate:** 12 hours

### Tasks

1. Define the selected fixture shape, matrix properties, right-hand side or
   input vector data, expected solution behavior, and failure modes.
2. Decide whether fixture data should be handwritten, generated by a small
   deterministic generator, or derived from existing corpus conventions.
3. Select metrics such as status, residual norm, solution norm, max absolute
   delta, structural checks, or family-specific diagnostics.
4. Define pass/fail tolerances and advisory rows for every metric that will be
   emitted.
5. Document the fixture and metric contract in working notes before code
   changes begin.

### Deliverables

- Fixture contract artifact.
- Metric and tolerance table.
- Expected row inventory.
- Fixture ownership decision.

### Completion Criteria

- The fixture is small enough for source control and deterministic CI use.
- Every planned report row has a metric definition and tolerance policy.
- The selected metrics support credibility without implying broad parity.

## Day 4: Reference Dependency Policy

**Title:** Reference Policy
**Theme:** Establish the external reference path and dependency-status
semantics.
**Time estimate:** 12 hours

### Tasks

1. Identify the exact reference implementation, executable path, library
   binding, or process model for the selected family.
2. Define dependency discovery behavior for installed, missing, version-mismatch,
   unsupported-platform, and execution-failure cases.
3. Decide which dependency-status rows are generated, advisory, required, or
   freshness-gated.
4. Define remediation text that is accurate on supported local and CI
   environments.
5. Record the dependency policy and any retained non-claims in working notes.

### Deliverables

- External reference dependency decision.
- Dependency-status row contract.
- Remediation wording draft.
- Unsupported-environment handling plan.

### Completion Criteria

- Missing dependencies produce structured diagnostics instead of ambiguous
  runner failures.
- Dependency policy is bounded to the selected family.
- Documentation wording cannot be read as broad external-library support.
