# Epic 21 Code Review (2026-11-23)

**Reviewed source:** `planning/epic-21`, created from merged `master` commit `230c46ca` (PR #250). Scope: 69 files under `src/`, 19 installed header inputs, 185 files under `tests/`, build/install manifests, workflows, public documentation, Epic 19–20 residuals and selected implementation paths. This is a source and evidence review; it is not a fresh numerical benchmark, platform certification or release approval. Severity describes the cost of the gap, not a claim of a newly reproduced defect. Paths and line numbers refer to this reviewed commit.

## Executive assessment

The library has substantial breadth: cross-linked sparse storage, compressed direct paths, LU/Cholesky/LDLT/QR, Krylov solvers, SVD/eigensolvers, reordering, Matrix Market input, static install metadata, 32/64-bit package-width controls and a large C/CI test surface. Epic 20 closed specific norm, matmul-output, package-width, workflow-policy and evidence-validator gaps. The post-closeout v5 timing workflow passed for PR #250's exact head, but compares byte-identical benchmark executables and establishes one narrow no-regression observation. The Epic 20 retrospective's blocked release and external-evidence boundaries remain the safe public interpretation.

**State-of-the-art verdict:** not established. A linked-list-first representation, several dense intermediates, limited independently accepted external solver evidence, one-cell timing evidence, no released candidate, and no shared/binary distribution contract preclude a general performance, scale or ecosystem claim. This is a judgment about *evidence and coverage*, not proof that every kernel is slow. For context, the official [SuiteSparse package inventory](https://github.com/DrTimothyAldenDavis/SuiteSparse) documents specialized sparse factorization packages, and [PETSc's KSP manual](https://petsc.org/release/manual/ksp/) documents a broad preconditioning and solver ecosystem. Neither source supplies a performance comparison to this repository. That comparison would require matched workloads, correctness gates and reproducible raw data.

## Detailed findings

### R21-01 — Matrix addition defeats its linear merge (high; efficiency)

[`src/sparse_matrix.c`](../../../../src/sparse_matrix.c) around lines 672–725 performs a two-pointer row merge, then calls `sparse_insert` for each retained result. The insertion path around line 368 scans the sorted row and column lists from their heads. Wide output rows therefore pay repeated scans even though the merge has already produced sorted columns. Sprint 218 fixed this pattern for `sparse_matmul`, not for addition. The hard-coded `1e-15` drop rule is also part of observable semantics and must be preserved until explicitly versioned. **Close:** reuse a proved append/link builder for sorted row output, compare dense-oracle values and ordering, sweep allocation failures, then measure wide-row scaling and peak memory. Do not infer total-library speed from this kernel.

### R21-02 — Physical-index arithmetic remains a caller trap (high; usability/coherence)

[`include/sparse_matrix.h`](../../../../include/sparse_matrix.h) correctly warns that `sparse_add`, `sparse_add_inplace` and `sparse_matmul` operate in physical space and must not receive matrices with nonidentity permutations. The implementation of `sparse_add` at line 672 checks dimensions but does not enforce that precondition. A user can therefore get a successful status for a mathematically different logical operation after a factorization or permutation. `sparse_add_inplace` also documents partial mutation on allocation failure. The warning is honest; the success status is still easy to misuse. **Close:** either define and implement logical-index behavior or reject permuted operands before mutation, with tests for both inputs, aliasing and failure atomicity. Do not silently change the algebraic meaning.

### R21-03 — Sparse low-rank output still allocates a dense intermediate by default (high; memory/efficiency)

[`src/sparse_svd.c`](../../../../src/sparse_svd.c) lines 1188–1252 describes an optional outer-product route but defaults to `calloc(m*n, sizeof(double))` for reconstruction. The optional path's own comment reports lower peak RSS on a selected fixture; this review did not reproduce that profile. The full SVD factors also consume dense storage, so removing the reconstruction accumulator would close only that *additional* memory cost, not make the full algorithm sparse-memory end to end. **Close:** validate bitwise/defined-tolerance output, error handling, memory and timing on a bounded corpus; promote the alternative as default only if the public contract and CI prove it. Document remaining dense factor memory.

### R21-04 — Numerical contract evidence is uneven across solver families (high; correctness/test coverage)

Sprint 217 added scaled norms and finite checks, but PR #241 review iterations found ordering regressions around initial/post-update convergence and overflow across CG, BiCGSTAB and MINRES; those were corrected case by case. [`src/sparse_iterative.c`](../../../../src/sparse_iterative.c) is 1,707 lines and [`tests/test_iterative.c`](../../../../tests/test_iterative.c) is 3,221 lines. No single cross-entry-point corpus establishes the same finite, zero-budget, breakdown, callback and final true-residual behavior for assembled, matrix-free and block variants. This is a *coverage gap*, not an assertion that current tests fail. **Close:** fund one family at a time with a shared oracle and exact status/iteration contracts, including extreme scales and failure injection; retain cross-compiler evidence before expanding the claim.

### R21-05 — 64-bit width is a package contract, not full algorithm coverage (medium; correctness/portability)

[`CMakeLists.txt`](../../../../CMakeLists.txt) and the Makefile now validate and export `SPARSE_IDX_BITS`; installed consumers reject mismatches. Epic 20 deliberately ran selected 64-bit paths only. Index-sensitive allocation, parsing and conversion code spans `sparse_matrix_io.c`, `sparse_csr.c` and direct backends. The installed width guard cannot prove that every algorithm works near the 32-bit boundary or with very large metadata. **Close:** choose a bounded input/conversion/solve route, exercise actual 64-bit builds with large *index metadata* without impractical memory allocation, and keep untested algorithms out of the claim.

### R21-06 — Core ownership and testing are hard to change safely (medium; maintainability)

The C source totals roughly 30k lines; `src/sparse_ldlt_csc.c` is 2,095 lines, `sparse_iterative.c` 1,707, `sparse_lu_csr.c` 1,594. The C test sources total roughly 73k lines, with several files over 3k lines. [`src/sparse_matrix_internal.h`](../../../../src/sparse_matrix_internal.h) combines linked-list storage, permutation maps, factor-state compatibility mirrors, a cached norm and optional mutex; comments explicitly identify a compatibility seam. The repository has useful internal modules, so a blanket rewrite would be risky. **Close:** split one ownership seam at a time, make invariant tests independent of implementation, preserve ABI/source compatibility, and require parity/sanitizer proof for each extraction.

### R21-07 — Static install is usable, but release acceptance remains unowned (high; usability/release coherence)

[`INSTALL.md`](../../../../INSTALL.md) provides tested Make/CMake static consumers and clearly rejects `BUILD_SHARED_LIBS=ON`. [Epic 20's closeout](../../EPIC_20/EPIC_20_RETROSPECTIVE.md) records no selected clean release candidate, approved changelog/version scope, signed release/rollback roles or candidate-specific archive and installed-consumer evidence. PR CI pass is source-head evidence, not an approved source-release asset. **Close:** establish a version/changelog and exact immutable candidate, reproduce archives, replay installed first use from the archive on named platforms, and obtain named product/security/release signoffs; otherwise retain `BLOCKED`. Do not fund shared-library ABI under the same acceptance ticket.

### R21-08 — External solver correctness and publication are separate open gates (high; evidence/documentation)

[`scripts/validate_external_baseline_evidence.py`](../../../../scripts/validate_external_baseline_evidence.py) closes the v1 format gap, while [Epic 20 Sprint 222](../../EPIC_20/SPRINT_222/RETROSPECTIVE.md) records two local 4×4 project/CHOLMOD pairs that remain `blocked` at environment provenance. There is no validator-accepted observed cell with complete actual loaded-library/BLAS provenance, repeated same-cell run and approved attribution/rights. **Close:** resolve those exact fields and independently inspect the bundle before publishing one narrowly worded cell. The validator must never be represented as having executed or authenticated the solver by itself.

### R21-09 — Timing pass is narrow and binary identity limits interpretation (medium; performance evidence)

[`sprint225-timing.yml`](../../../../.github/workflows/sprint225-timing.yml) runs three paired v5 macOS jobs and a fail-closed decision. The PR #250 current-head run `45112328984` passed; local audit of original ZIPs found 50 ordered side trials per job and matching hashes. However, baseline and candidate `src/`, `include/`, benchmark source and Makefile content are identical, and each job reports identical benchmark executable hashes. The measured ratios therefore test hosted stability/no regression for this cell, not an implementation speed improvement. The original binaries are not in the archive. **Close:** for a future performance claim, predeclare a *differing* candidate kernel, retain executable bytes or reproducible build attestation, compare independent correctness and multiple representative matrices, and limit claims to the tested hosts.

### R21-10 — Evidence tools and public docs need a sustainable source of truth (medium; maintainability/documentation)

`tests/test_api_docs_local_only_guard.py` exceeds 4,300 lines; `scripts/run_external_comparison.py` and `scripts/normalize_report_index.py` exceed 2,000. The extensive tests are valuable, but workflow inventory counts and exact-head references have repeatedly needed manual updates. [`README.md`](../../../../README.md) now has a good start-here map, while [`INSTALL.md`](../../../../INSTALL.md), [`benchmarks/README.md`](../../../../benchmarks/README.md) and planning retrospectives preserve many historical and current-status qualifiers. **Close:** modularize one policy/evidence tool with frozen output contracts, drive inventory assertions from a declared manifest, and add a generated current-capabilities table backed by executable checks. Keep historical evidence in planning files and current user guidance concise.

## Test and risk assessment

The Make/CMake suite has 62 C test sources plus a focused CTest selector; CI spans Linux, macOS, Windows MSVC, sanitizers, static install, selected 64-bit lanes, policy mutations and hosted selected evidence. This is substantial coverage and justifies confidence in the *named* paths. It does not prove broad numerical conformance, large-scale memory behavior, all 64-bit algorithms, reproducible binary packaging or cross-version ABI. The reviewer did not rerun the full suite for this documentation-only review; the last exact PR-head CI result was 26 passing checks on `632266d4`, and this branch starts at merged `230c46ca`.

## Explicit portfolio boundary

Epic 21 should close R21-01/02 as one arithmetic owner; R21-03 as one memory owner; R21-04 in two named solver-family owners; R21-05 as one width route; R21-06/10 as bounded maintenance owners; and R21-07/08/09 only when their external evidence and approval gates are actually met. Shared-library ABI, package-manager distribution, GPU/distributed-memory computing, broad Windows solver parity and general state-of-the-art ranking require separate product scope. A sprint that produces a blocked receipt has preserved integrity, but has not closed its proposed capability.
