# Sprint 152 Day 2 Generated Family Candidate Audit

## Purpose

Day 2 audits generated report families for Sprint 152 freshness-policy
promotion. The audit compares each family by claim value, determinism, command
stability, artifact cost, local/CI suitability, failure clarity, and
claim-boundary risk before Day 3 selects the families for closure.

## Scoring Model

Scores use a 1-5 scale for each column:

- **Claim value:** how directly the family supports current claim-bearing
  evidence.
- **Stability:** command/path/determinism maturity.
- **Suitability:** ability to run locally or in CI without excessive runtime,
  platform, or dependency risk.
- **Failure clarity:** whether failures can name the missing/stale row and
  remediation command.
- **Boundary safety:** whether the family can avoid broad release, platform,
  package, performance, or state-of-the-art overclaims.

Higher totals are better candidates for Sprint 152 promotion.

## Per-Family Findings

### Oracle

The `oracle/generated_reference` and `oracle/solver_backed` families are the
strongest Sprint 152 candidates. They directly support recent QR and
partial-SVD maintained corpus claims, are generated by a single Python command
surface, and already carry command, commit, branch, platform, compiler,
configuration, support tier, artifact path, claim scope, and non-claim fields.

Current gaps:

- `freshness_status` remains `generated_present_unchecked` even when
  `source_commit` matches current `HEAD`.
- Strict comparison still uses broad family-level behavior rather than
  selected-row or selected-subfamily policy.
- Failure messages identify generated-present/stale status but do not yet name
  all selected expected row counts or remediation commands.

Recommended posture: select for Sprint 152 closure and decide whether the
oracle family becomes required locally while preserving `local_only` support
tier and no hosted-CI proof.

### Report Index Missing-Generated Rows

The `report_index/missing_generated` family is not solver evidence, but it is
important policy infrastructure. It makes absent generated reports visible as
`not_generated` instead of silently omitting rows.

Current gaps:

- Missing-generated behavior is family-level; selected families may need more
  precise missing-row diagnostics.
- Required generated family failures should name the regeneration command and
  selected policy owner.

Recommended posture: select as supporting infrastructure for oracle freshness
promotion.

### Corpus Source-Controlled Families

`corpus/fixtures`, `corpus/generators`, and `corpus/expected` are prerequisites
for generated freshness but are governed by Git and schema validation. They
should not be reclassified as generated freshness rows.

Recommended posture: keep as source-controlled prerequisite rows and use
`python3 scripts/validate_corpus_schema.py` in validation.

### Benchmark

`benchmark/canonical` rows have useful local measurement value but are not
good required-freshness candidates for Sprint 152. The command can be expensive
and the row meaning is threshold-free local measurement, not release
performance proof.

Current gaps:

- Runtime cost and local machine variance are higher than oracle generation.
- Freshness should not imply portable performance or superiority.
- Failure messages need careful wording if this family becomes required.

Recommended posture: defer required promotion; possibly keep advisory
normalization/freshness checks.

### Sentinel

`sentinel/runtime` hard-gate rows have higher claim value than benchmark rows
because they encode bounded local pass/fail behavior. They still carry
performance- and backend-policy overclaim risk.

Current gaps:

- Hard-gate semantics must remain limited to explicitly thresholded local
  lanes.
- Runtime cost and platform drift need policy decisions.
- Advisory sentinel rows should not become required by accident.

Recommended posture: consider advisory-only or defer required promotion unless
Day 3 selects a very narrow local hard-gate freshness lane.

### Guardrail

`guardrail/large_matrix` rows preserve structural or bounded local checks, but
they are farther from the immediate Sprint 150/Sprint 151 corpus freshness
residual.

Current gaps:

- Runtime and artifact costs are less predictable than oracle report
  generation.
- Broad scalability and memory-footprint overclaim risk is higher.

Recommended posture: defer required promotion; retain as future candidate.

### Dead Code

`deadcode/report` rows are useful maintainer triage evidence and CI uploads the
artifacts. They should remain advisory because they do not prove zero dead
code, semantic correctness, or removal readiness.

Recommended posture: keep advisory; do not select for required freshness in
Sprint 152 unless all higher-value oracle work is complete.

### Coverage

`coverage/src` rows are supplemental and tree-mutating. Coverage artifacts are
tool- and platform-sensitive and do not prove behavioral completeness.

Recommended posture: keep advisory/deferred for generated freshness promotion.

### Package And CI

`package/static_install` and `ci/reviewed_lanes` are source-controlled proof
owner or lane-definition rows. They point to maintained commands and hosted
lanes but do not create local generated report freshness evidence.

Recommended posture: keep source-controlled; update docs only if Sprint 152
needs to clarify that hosted logs remain external evidence.

## Advisory Or Deferred Candidates

Recommended advisory/deferred families for Day 3:

- `benchmark/canonical`: advisory due to runtime and variance.
- `sentinel/advisory`: advisory by row meaning.
- `sentinel/runtime`: defer required promotion unless narrowly selected.
- `guardrail/large_matrix`: defer required promotion.
- `deadcode/report`: advisory triage evidence.
- `coverage/src`: advisory supplemental evidence.
- `package/static_install`: source-controlled proof owner only.
- `ci/reviewed_lanes`: hosted external lane definition only.

## Day 3 Inputs

The best Day 3 selection is likely:

1. Select `oracle/generated_reference` and `oracle/solver_backed` for generated
   freshness publication.
2. Select `report_index/missing_generated` as supporting missing-report policy.
3. Keep corpus source-controlled families as prerequisites.
4. Keep benchmark, sentinel, guardrail, dead-code, coverage, package, CI,
   documentation, and runtime-backend rows advisory/source-controlled/deferred
   unless Day 3 identifies a smaller safely closable subset.
