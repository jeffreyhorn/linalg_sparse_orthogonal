## Handoff Summary

Sprint 145 must simplify adoption without expanding prior evidence:

- QR is supported by bounded fixture-local corpus evidence and must not become
  a broad QR, LAPACK, NumPy, SciPy, SuiteSparse, platform, performance, or
  state-of-the-art claim.
- Partial-SVD is supported by bounded vector residual, subspace/projector,
  convergence, and fail-closed evidence and must not become broad SVD parity or
  performance evidence.
- Report rows are source-controlled schema and proof-owner metadata; generated
  reports remain fresh only when regenerated by maintained commands.
- Runtime/backend sentinels guide governance and regressions; they do not prove
  portable performance or package behavior.
- Package support is static-first only; shared-library ABI, loader,
  package-manager, and static/shared selector claims remain deferred.
- Platform support tiers are explicit: Linux is strongest reviewed source of
  truth, macOS has reviewed static-first install/export proof, and Windows
  remains CMake-first with supplemental install/downstream confidence.

## Initial Adoption Success Criteria

A Sprint 145 adoption change is successful when:

1. A first-use reader can find the shortest path to build/install the library.
2. The reader can choose an appropriate solver family without parsing the full
   maintainer evidence record.
3. The reader can run a maintained solve example and find diagnostics.
4. Advanced controls, benchmark interpretation, report semantics, and
   maintainer evidence are linked but not forced into the first-use path.
5. Public docs and headers preserve all numerical, runtime, package, and
   platform non-claims from Sprints 139-144.
6. Touched examples, docs, reports, install paths, and headers pass their
   required validation gates.

## Initial Non-Claim Register

Sprint 145 must not imply:

- broad QR, SVD, partial-SVD, LAPACK, NumPy, SciPy, or SuiteSparse parity;
- broad repeated-spectrum, rank-deficient, sparse-output, convergence-rate, or
  performance guarantees beyond bounded fixtures and maintained proof;
- source-controlled generated reports as fresh report runs;
- runtime/backend portable performance parity;
- shared-library build/install/export support;
- dynamic ABI compatibility;
- runtime-loader compatibility;
- package-manager availability;
- static/shared package selector support;
- Windows Makefile parity;
- Windows `pkg-config` parity;
- Windows reviewed install-validation parity;
- Windows staged test closure;
- broad macOS platform parity beyond reviewed static-first install/export
  proof;
- state-of-the-art status from documentation polish.

## Initial Validation Requirements

| Surface changed | Validation requirement |
| --- | --- |
| Markdown docs | `git diff --check`, relevant stale-wording scans, unsupported-claim scans, and local link/reference checks where available. |
| Examples | Focused example compile/build/run checks for any maintained example touched. |
| README/INSTALL package commands | Install/downstream checks as needed, including `tests/test_install.sh` and `tests/test_cmake_install.sh` if package commands change. |
| Report-family rows or report docs | `python3 scripts/validate_corpus_schema.py` and relevant `scripts/normalize_report_index.py` checks. |
| Public headers or C files | `make format && make lint && make test` before proceeding. |

## Stop Conditions

Stop and ask for direction if:

- a proposed simplification would erase an earned support boundary instead of
  routing it to a deeper link;
- public header cleanup would change public API behavior, ABI posture,
  ownership rules, or error semantics;
- a proposed example requires unplanned solver, package, runtime, or platform
  behavior;
- validation fails after focused fixes;
- adoption docs would claim broad numerical parity, package-manager support,
  shared-library ABI support, Windows parity, portable performance parity, or
  state-of-the-art status without direct proof;
- the Day 2 audit cannot produce a ranked fix shortlist for Day 3 design.
