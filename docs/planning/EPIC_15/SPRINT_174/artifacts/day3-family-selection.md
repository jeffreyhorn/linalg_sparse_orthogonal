# Day 3: Family Selection Decision

## Purpose

Select exactly one bounded external comparison family for Sprint 174 and
define the initial fixture, comparator, tolerance, report, and claim boundary
before implementation begins.

## Selected Family

Sprint 174 selects:

```text
linked-list LU generated comparison on lu_nonsym_square_5
```

The selected family will add one generated comparison report family for the
existing linked-list LU dense-reference lane. It will not add LU CSR, CSR/CSC
public solve API, singular-matrix report, broad nonsymmetric ecosystem, or
external-library parity claims.

## Selection Rationale

The Day 2 ranking placed linked-list LU first because it has the best balance
of:

- high user value: general square nonsymmetric solving is a core workflow;
- existing source-controlled dense reference helper:
  `tests/lu_external_dense_reference.py`;
- existing deterministic C fixture and test:
  `tests/test_sparse_lu.c`;
- simple report metrics: status, residual norm, solution norm, solution
  values, and max absolute project-vs-baseline delta;
- clean claim containment: one fixture, one solver family, one comparator,
  one tolerance family;
- lower implementation risk than new LU CSR, iterative, or eigensolver
  comparison architectures.

LDLT CSC KKT and Cholesky CSC SPD remain strong alternatives, but they carry
more Day 3 risk for this sprint: LDLT wording must avoid pivot/factorization
layout implications, and Cholesky CSC report rows must choose Matrix Market
path and reorder semantics. Linked-list LU gives Sprint 174 the cleanest path
to a complete added generated comparison family.

## Selected Comparator

The comparator is the source-controlled Python helper:

```text
tests/lu_external_dense_reference.py
```

For `lu_nonsym_square_5`, the helper:

- builds the same 5x5 dense nonsymmetric matrix as the C test fixture;
- constructs the right-hand side from `x_true = [1, 2, 3, 4, 5]`;
- solves with a local dense Gaussian elimination implementation;
- emits `OK 5` followed by the dense reference solution.

Day 3 observed the helper output:

```text
OK 5
1
2
3.0000000000000004
4
4.9999999999999991
```

The helper is suitable because it is source-controlled, deterministic, local,
already used by `tests/test_sparse_lu.c`, and does not require optional
external package availability to produce pass evidence.

## Initial Tolerance Policy

| Metric | Proposed tolerance | Rationale |
| --- | ---: | --- |
| residual norm | `1e-10` | Matches the existing C external LU test residual threshold. |
| solution max absolute delta | `1e-10` | Matches the existing C external LU solution assertions. |
| solution values | `1e-10` | Keeps report rows aligned with the existing deterministic fixture. |
| solution norm | `1e-10` absolute delta | Useful diagnostic; bounded to the same fixture-local solution vector. |

The exact Day 4/Day 5 schema may refine row names, but it must preserve these
tolerances unless implementation evidence justifies a tighter or looser
fixture-local threshold.

## Bounded Claim

Sprint 174 may claim only this after implementation and validation:

> The project has one generated local comparison report family for linked-list
> LU on `lu_nonsym_square_5`, comparing the project solve result against the
> source-controlled dense LU reference helper with fixture-local residual and
> solution-delta tolerances.

The claim is local generated evidence unless and until a reviewed hosted lane
explicitly includes the selected comparison freshness gate and uploads the
selected artifacts.

## Explicit Non-Claims

The selected LU comparison does not claim:

- LU CSR correctness;
- direct CSR/CSC public LU solve API coverage;
- broad linked-list LU correctness;
- broad nonsymmetric solver parity;
- singular-matrix report-family coverage;
- pivoting-strategy superiority;
- factorization-layout or internal pivot identity;
- LAPACK, NumPy, SciPy, SuiteSparse, Eigen, PETSc, Trilinos, or broad
  external-library parity;
- release evidence;
- broad platform support;
- package-manager support;
- shared-library ABI support;
- runtime-loader behavior;
- performance superiority;
- state-of-the-art sparse linear algebra status.

## Acceptance Criteria For Days 4 Through 12

Implementation may proceed only if Days 4 through 12 preserve these criteria:

- one family, one fixture, one comparator, and one target are added;
- generated outputs live under `build/comparison/lu_nonsym_square_5/`;
- source-controlled proof-owner rows are added before generated rows are
  treated as selected evidence;
- `make report-index-comparison-freshness` is updated only after the LU target
  is generated and freshness-checked;
- missing or failing helper output cannot become pass evidence;
- generated rows use current source commit metadata and fail freshness when
  stale;
- focused tests cover the new comparison runner path;
- public and maintainer docs name the exact fixture and non-claims;
- package/static/shared ABI deferral guards pass if wording touches those
  support surfaces;
- if `.c` or `.h` files change, run `make format && make lint && make test`.
