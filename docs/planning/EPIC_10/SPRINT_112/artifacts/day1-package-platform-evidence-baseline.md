# Day 1 Package and Platform Evidence Baseline

## Purpose

Day 1 establishes the live package, ABI, and cross-platform evidence map for
Sprint 112. The goal is to start package and platform work from explicit
support truth rather than turning existing install checks, unchanged public
headers, or CI subsets into broader claims.

## Package Surface Inventory

| Surface | Live owner | Baseline behavior | Sprint 112 use |
|---|---|---|---|
| Make install | `Makefile` | Installs `libsparse_lu_ortho.a`, public headers, generated `sparse_version.h`, and `sparse.pc` under `PREFIX`/`DESTDIR`; supports `uninstall`. | Audit and validate Unix-side static install truth. |
| CMake install/export | `CMakeLists.txt` | Installs static target export, public headers, generated version header, config/version files, and pkg-config metadata. | Audit and validate installed CMake consumer truth. |
| CMake config template | `cmake/SparseConfig.cmake.in` | Includes installed `SparseTargets.cmake` and checks package components. | Keep as `find_package(Sparse)` package entry. |
| CMake version file | generated by `write_basic_package_version_file(...)` | Uses `COMPATIBILITY ExactVersion` to avoid overstating ABI compatibility. | Treat as evidence for exact package versioning, not ABI stability. |
| pkg-config template | `sparse.pc.in` | Emits `-I${includedir}`, `-lsparse_lu_ortho`, `-lm`, and optional thread/OpenMP flags. | Validate downstream compile/link flags. |
| Make install proof | `tests/test_install.sh` | Stages install, rejects shared artifacts, verifies installed headers and pkg-config, compiles/runs consumers, and checks uninstall. | Baseline proof for Days 5-6. |
| CMake install proof | `tests/test_cmake_install.sh` | Stages CMake install/export, verifies installed package files, builds `find_package(Sparse)` example, and checks exact-version behavior. | Baseline proof for Days 5 and 7. |
| Installed consumer example | `examples/cmake_example/` | Minimal downstream CMake consumer using installed `Sparse::sparse_lu_ortho`. | Primary installed-consumer example. |
| User install docs | `INSTALL.md` | Operational setup, staged installs, installed-consumer workflows, verification scripts, and platform notes. | Primary public install/package authority. |
| README install summary | `README.md` | Compact install and package summary, with link to `INSTALL.md` for detail. | Keep concise; do not turn into proof-owner document. |
| Maintainer package docs | `docs/maintainer_guide.md` | Static-first package/ABI contract, focused install regression ownership, and platform evidence interpretation. | Primary detailed proof/evidence surface. |

## Validation Expectations

| Touched surface | Required checks |
|---|---|
| Documentation only | `git diff --check`; trailing-whitespace scan over touched docs; relative link check when Markdown links change. |
| `Makefile`, `sparse.pc.in`, or Make install semantics | `bash tests/test_install.sh`; `git diff --check`; stronger C checks if code/header files also change. |
| CMake install/export/package files | `bash tests/test_cmake_install.sh`; focused CMake configure/build/install; `git diff --check`. |
| Downstream consumer example files | Build or run the relevant consumer proof; avoid private headers. |
| Public headers or installed-header behavior | Public/install-header drift review; `make format && make lint && make test`; install checks if package semantics change. |
| CI workflow files | Review claim wording against available platform evidence and run closest local equivalent where possible. |
| Mixed build/package/code/doc change | Run the strongest check required by any touched surface. |

## Day 1 Conclusions

- Sprint 112 starts with a maintained static-first package story, not a
  shared-library or dynamic-ABI support story.
- Sprint 110 no-public-header drift is useful baseline evidence, but it cannot
  be promoted to ABI stability or broader Windows coverage.
- Linux remains the strongest reviewed platform source of truth.
- macOS has a reviewed Apple Clang path and supplemental static-first package
  confidence, but not full reviewed install/export parity.
- Windows remains a CMake-first reviewed subset with explicit staged
  exclusions and no separate reviewed install-validation lane.
- Day 2 should audit package surfaces before Day 3-4 decide support-tier
  promotion or static-first preservation.
