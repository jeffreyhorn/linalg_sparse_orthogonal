# Day 2 Package Surface Audit

## Purpose

Day 2 audits the live package, install, export, versioning, and downstream
consumer surfaces before Sprint 112 makes an ABI support decision or changes
package/platform wording. The audit ties behavior to concrete files and
commands, then orders proof gaps for later sprint days.

## Make Install Audit

| Area | Live behavior | Source |
|---|---|---|
| install target | `make install` depends on the static library and generated version header. | `Makefile` |
| default prefix | `PREFIX ?= /usr/local`. | `Makefile` |

## Support-Claim Audit

| Claim | Status | Notes |
|---|---|---|
| Static archive package is maintained. | Supported by current surfaces. | Make, CMake, install scripts, README, INSTALL, and maintainer guide agree. |
| `pkg-config` consumer path is maintained. | Supported on Unix-side install surface. | `tests/test_install.sh` compiles/runs pkg-config consumers. |
| CMake `find_package(Sparse)` consumer path is maintained. | Supported. | `tests/test_cmake_install.sh` builds and runs installed CMake example. |
| Package version metadata is single-sourced. | Supported. | `VERSION` drives generated header, CMake package version, and pkg-config version. |
| CMake package version compatibility implies ABI compatibility. | Not supported. | Compatibility is exact-version only and intentionally avoids ABI overclaiming. |
| Shared-library package is supported. | Not supported. | Package story is static-first; install scripts reject shared artifacts. |
| Dynamic ABI compatibility is supported. | Not supported. | No symbol/versioning/release ABI proof lane exists. |
| Windows install validation is reviewed. | Not supported. | Windows remains reviewed CMake-first consumer subset only. |
| macOS install/export parity is reviewed. | Not supported. | macOS Make install/pkg-config job is supplemental confidence, not reviewed parity. |

## Stale, Unsupported, Ambiguous, or Overbroad Claims

No blocking public-package overclaim was found on Day 2. The major boundaries
are already documented:

- static-first package surface is maintained;
- shared-library packaging is deferred;
- dynamic ABI compatibility is not promised;
- Windows does not claim a separate install-validation lane;
- macOS install/pkg-config proof is supplemental.

Potential wording risks to preserve during later days:

- Do not use Sprint 110 no-public-header drift as shorthand for ABI stability.
- Do not describe exact-version CMake package matching as dynamic ABI support.
- Do not describe local Unix install scripts as symmetric reviewed coverage
  across Linux, macOS, and Windows.
- Do not treat the macOS supplemental install/pkg-config job as reviewed
  install/export parity.
- Do not treat the Windows CMake-first consumer subset as Makefile or separate
  install-validation support.

## Ordered Proof Gaps

1. Define the evidence required for any shared-library or dynamic-ABI claim.
2. Decide whether Sprint 112 preserves static-first support or attempts a
   broader ABI/shared-library proof.
3. Turn `tests/test_install.sh` and `tests/test_cmake_install.sh` into the
   concrete proof plan for the selected support tier.
4. Run Make install, CMake install/export, pkg-config, and downstream consumer
   proof against staged prefixes.
5. Reconcile platform-tier wording after install/export proof is refreshed.
6. Update public and maintainer docs only after evidence is captured.

- Package behavior is tied to concrete files, scripts, and commands.
- Unclear support claims are identified before documentation changes.
- Install/export proof gaps are ordered for later Sprint 112 days.
