# Day 5 QR Fixture Boundary

## Purpose

Day 5 defines the safe cleanup boundary for `tests/test_qr.c` before any QR
test code is edited. The Day 6 cleanup should reduce repeated matrix and RHS
setup while keeping QR solve, rank, residual, reconstruction, orthogonality,
mode-comparison, and refinement proof intent visible at the test sites.

## File Snapshot

- File: `tests/test_qr.c`
- Current size: 3,234 lines
- Existing local helpers:
  - `qr_reconstruction_error`
  - `assert_qr_reconstruction_below`
  - `compute_rel_residual`
  - `assert_qr_true_residual_below`
  - `compare_dense_sparse_qr`

The existing helpers already cover high-value assertion behavior. Day 6 should
not introduce a shared helper header or a compiled helper target.

### Safe RHS Builders

These are safe if kept small and named literally:

- sequential RHS `b[i] = i + 1` for loaded matrices and dense/sparse QR
  comparison paths;
- exact-solution RHS generated by `x_exact[i] = i + 1` then `sparse_matvec`;
- fixed small RHS arrays should usually remain inline because they explain the
  analytical proof.

### Assertion Helpers

Existing assertion helpers are sufficient for Day 6. Additional assertion
helpers are not selected because they would hide important QR proof intent:

- rank checks;
- R diagonal ordering checks;
- permutation validity checks;
- least-squares residual expectations;
- full-vs-economy solution comparisons;
- dense-mode-vs-sparse-mode comparisons;
- iterative refinement monotonicity checks.

## Inline-Proof Preservation Rules

Day 6 must keep these statements visible at the call sites:

- expected rank values and rank inequalities;
- QR/LU solution agreement checks;
- reconstruction tolerances and labels;
- residual thresholds and reported-vs-true residual comparisons;
- sparse-mode-vs-dense-mode solution comparisons;
- refinement before/after residual comparisons;
- permutation validity and R triangularity checks.

The builder call should explain only the input shape, not the expected QR
result.

## Placement and Naming

- File: `tests/test_qr.c`
- Placement: after the forward declarations and before the first test section
- Linkage: `static`
- Return convention: return `SparseMatrix *` or `NULL`; tests retain the
  existing `ASSERT_NOT_NULL(A); if (!A) return;` pattern
- Build-system impact: none

No public header, internal header, Makefile, CMake, or test-registration
change is needed.

No CTest registration count check is expected because Day 6 should not add,
remove, or rename `RUN_TEST` entries.
